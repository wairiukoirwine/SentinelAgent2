1. PROJECT IDENTITY AND RESEARCH PURPOSE
======================================================================

Project name: SentinelAgent

Research title:
"Design and Evaluation of a Policy-Enforced Security Gateway for Indirect Prompt Injection in a Simulated AI Agent."

Academic context:
DAI034 Capstone Project, Africa International University.
Track: Secure AI Applications.

Core problem:
An AI agent reads an external document that contains untrusted content. The document may contain instructions that attempt to override the user's original request or manipulate the agent into performing an unsafe tool action. For example, a document may instruct the agent to send confidential information to an unapproved recipient.

The project demonstrates how content-level detection and a policy-enforced security gateway can reduce unsafe tool execution in a controlled simulation.

The system must:
- Simulate an agent that reads documents.
- Treat document contents as untrusted input.
- Allow the agent to propose actions.
- Inspect proposed actions using configurable security controls.
- Enforce gateway decisions before protected mock-tool execution.
- Record decisions and outcomes.
- Compare four experimental configurations.
- Calculate and present security, utility, and performance metrics.

The project is an experimental prototype, not a production email system, general-purpose autonomous agent, or claim of complete prompt-injection prevention.

2. NON-NEGOTIABLE SAFETY BOUNDARIES
======================================================================

These restrictions apply to development, testing, demonstration, and the final application.

2.1 Fake data only
- Use synthetic documents written for this project.
- Use fictional names and fictional recipient addresses.
- Use synthetic content and synthetic data labels.
- Never place real university records, student information, staff information, passwords, API keys, private messages, or confidential business data in the test corpus.
- Do not use real confidential information as a test payload.

2.2 Mock tools only
The only tools available to the simulated agent are:
- read_document
- send_email

Both must be local mock implementations.
- read_document reads only from the project's approved local synthetic-document directory or scenario store.
- send_email records a simulated email event in local storage or an in-memory/SQLite event log.
- send_email must never connect to SMTP, an email provider, an external API, or a real recipient.
- Do not implement arbitrary shell, filesystem, browser, network, database-administration, or external tool access for the agent.
- Do not add a real email integration as an optional feature.

2.3 Security boundaries
- The user task, approved recipient allowlist, data labels, and trusted policy configuration must be held outside the untrusted document content.
- A document must not be able to modify the user's original task, allowlist, data classification, gateway rules, or approval state.
- Document text is data to be processed, not authority to change system policy.
- All protected mock-tool execution must pass through the gateway.
- The frontend must not execute mock tools directly.
- The simulated agent must not call the mock executor directly in protected configurations.
- BLOCK must prevent execution.
- REVIEW must not execute until an explicit, recorded approval is provided.
- Missing gateway, gateway exception, malformed action, missing policy data, or unavailable required security component must fail closed in protected configurations.
- Never convert an exception or missing result into ALLOW.
- Record the decision, reason, approval status, and execution outcome.
- Keep the baseline experiment isolated and clearly labelled as intentionally unprotected.

2.4 No real-world side effects
No real emails, external messages, purchases, file uploads, account changes, external service calls, or actions against real systems are permitted.

5. HIGH-LEVEL SYSTEM ARCHITECTURE
======================================================================

Expected logical flow:

User selects a scenario and starts a simulation in the React frontend.
The frontend sends a request to FastAPI.
FastAPI loads the trusted user task, scenario metadata, document reference, approved recipients, and data labels from trusted application state.
The simulated agent reads the synthetic document through read_document.
The document content is marked and handled as untrusted input.
The agent produces a proposed action, if the scenario requires one.
The configured content detector evaluates the untrusted content when enabled.
The action and relevant trusted context are passed to the policy gateway when enabled.
The gateway returns ALLOW, BLOCK, or REVIEW.
Only the authorized mock execution layer can execute a protected action.
The mock executor records a simulated result.
The application records audit events and experiment measurements.
Results are persisted in SQLite/JSON/CSV.
The frontend retrieves real results from the backend and renders them.

Logical components:
A. React frontend.
B. FastAPI API layer.
C. Scenario manager.
D. Simulated agent.
E. Mock tool registry and executor.
F. Content detector adapter.
G. Policy gateway.
H. Experiment runner.
I. Metrics calculator.
J. Audit logger.
K. Persistence layer.
L. Reporting/export layer.

The architecture must keep the detector and gateway logically separate so that they can be independently enabled or disabled for the four experiments.

8. SIMULATED AGENT AND MOCK TOOL BEHAVIOR
======================================================================

8.1 Simulated agent
The agent must be deterministic enough for repeatable experiments.
It does not need an external LLM.
It should:
- Receive a trusted user task and scenario.
- Request the scenario document through read_document.
- Mark the returned document as untrusted.
- Process the content according to a transparent, documented simulation strategy.
- Produce a proposed action only when the scenario logic indicates one.
- Never directly execute send_email.
- Submit proposed actions to the configured security pipeline.
- Return a structured result explaining the action and final outcome.

If the project uses a rule-based simulated agent, explicitly describe it as a simulated agent, not a real language model. Do not imply that a deterministic scenario engine reproduces all behavior of commercial LLM agents.

8.2 read_document
- Accept only a valid document ID or scenario-authorized reference.
- Read only synthetic documents stored within the project's controlled data directory or scenario store.
- Reject path traversal and arbitrary filesystem paths.
- Return document content and metadata.
- Mark content as untrusted.
- Log the read event.
- Do not execute content.

8.3 send_email
- Accept only structured mock email arguments.
- Never perform network activity.
- Never send real email.
- Record a simulated email event in SQLite or a local event store.
- Validate recipient format for the simulation.
- Preserve recipient and data-label information for policy evaluation.
- Return a clearly marked simulated execution result.

8.4 Tool executor
- Centralize mock tool execution.
- In protected configurations, only the gateway can authorize execution.
- Do not expose direct executor methods to the frontend.
- Enforce tool allowlisting.
- Reject unknown tool names.
- Record execution attempts and outcomes.
- Provide tests proving that blocked/review-pending actions are not executed.

8.5 Baseline configuration
The no-gateway configuration is intentionally unprotected for experimental comparison. It may execute the proposed mock action in the isolated simulator. It must still use mock tools only and must not create real-world side effects.

9. CONTENT DETECTION INTEGRATION
======================================================================

The content detector is a separate control from the policy gateway.

9.1 Interface
Provide a stable adapter similar to:
check_content(text: str) -> DetectorResult

The exact return model must be agreed with the detector contributor and documented.

9.2 Detector behavior
- Evaluate document content as untrusted.
- Return a structured result.
- Preserve the detector method and threshold used.
- Make errors explicit.
- Do not silently convert detector errors into a clean result.
- In configurations where detection is enabled, detector failure must be handled safely and must not result in an unsafe ALLOW.
- Keep the detector switch independent from the gateway switch.

9.3 Keyword detector
- May be used as an additional baseline or supporting method.
- Document keywords and limitations.
- Avoid claiming that keyword matching detects all prompt injections.
- Test benign text containing suspicious-looking terms to measure false alarms.

9.4 Threshold and data separation
- Use development data for threshold selection.
- Use validation data for development checks.
- Reserve final-test scenarios from tuning.
- Document any overlap or leakage if it occurs.
- Report precision, recall, confusion matrix, false positives, false negatives, and sample counts.

======================================================================
10. POLICY GATEWAY
======================================================================

The gateway is the enforcement point for protected mock-tool actions.

10.1 Decision values
- ALLOW: action satisfies applicable policy and may be executed.
- BLOCK: action violates policy and must not execute.
- REVIEW: action requires explicit recorded human approval before execution.

10.2 Trusted policy inputs
- Original user task.
- Tool name and arguments.
- Recipient.
- Trusted data label.
- Approved recipient list.
- Detector result when enabled.
- Current experiment configuration.
- Existing recorded approval state.

Document content must never be the source of authority for changing these values.

10.3 Minimum policy checks
Implement explicit, testable rules for:
- Unknown or disallowed tool.
- Missing or malformed action fields.
- Confidential data sent to an unapproved recipient.
- Recipient outside the allowlist.
- Action unrelated to or inconsistent with the original user task, according to the defined policy.
- Suspicious detector result when detector is enabled.
- Missing detector result when detector is required.
- Missing gateway configuration.
- Policy evaluation exception.
- REVIEW requiring approval.
- Duplicate or invalid approval.
- Attempt to execute after BLOCK.
- Attempt to execute before approval.

The team must document the rule ordering and rationale. Do not invent hidden policy behavior.

10.4 Fail-closed behavior
In protected configurations:
- If the gateway is unavailable, do not execute.
- If policy evaluation throws an exception, do not execute.
- If required inputs are absent, do not execute.
- If detector is enabled but its result is missing or errored, do not treat it as safe.
- If approval is required but not recorded, do not execute.
- If decision cannot be parsed, do not execute.
- Log the failure and reason.

10.5 Approval
- REVIEW creates a pending review record.
- Approval must be a separate explicit action.
- Store who/what approved, when, the action ID, and approval decision.
- Only an approved pending action can proceed to mock execution.
- Rejection or expiration must prevent execution.
- Do not infer approval from document content or user-provided document instructions.
- For a local academic prototype, a simulated reviewer identity is acceptable if clearly labelled as simulated.

11. FOUR EXPERIMENTAL CONFIGURATIONS
======================================================================

The evaluation must compare exactly these four principal configurations.

Configuration A: Baseline / No Gateway
- Content detection OFF.
- Policy gateway OFF.
- Simulated action follows baseline execution behavior.
- Mock tools only.
- Clearly label this configuration as intentionally unprotected.

Configuration B: Content Check Only
- Content detection ON.
- Policy gateway OFF.
- Detector output is recorded and used according to the agreed content-only experimental behavior.
- Define precisely whether suspicious content prevents the simulated action or only flags it. Do not leave this ambiguous.
- Mock tools only.

Configuration C: Policy Gateway Only
- Content detection OFF.
- Policy gateway ON.
- Gateway evaluates trusted action context and policy rules without detector output.
- Protected mock execution must pass through gateway.

Configuration D: Combined Controls
- Content detection ON.
- Policy gateway ON.
- Detector result is supplied to gateway.
- Gateway enforces the final action decision.
- Protected mock execution must pass through gateway.

Important experimental design issue:
The original project describes a comparison of "content check only" and "policy only." The team must document the exact enforcement behavior in Configuration B so that it is a valid and reproducible control condition. Keep the behavior consistent for all scenarios. Do not quietly give Configuration B a full policy gateway.

The same scenario definitions and comparable conditions must be used across all four configurations. Do not change scenario difficulty between configurations.

12. SCENARIO DATASET DESIGN
======================================================================

Use synthetic, labelled scenarios. A suggested initial target is 24 curated scenarios, with an appropriate development/validation/final-test split. This is a starting target, not a statistically sufficient sample by itself.

Suggested scenario categories:
- Benign document with harmless content.
- Benign document containing words that may trigger simple keyword rules.
- User explicitly requests a permitted simulated email.
- Document includes an instruction to ignore prior instructions.
- Document attempts to change the original user task.
- Document asks to disclose confidential information.
- Document asks to send information to an unapproved recipient.
- Document tries to change the approved recipient.
- Document contains an instruction disguised as ordinary content.
- Document contains conflicting or ambiguous instructions.
- Document contains a suspicious instruction but no proposed tool action.
- Document requests an action that should require REVIEW.
- Document includes irrelevant instructions unrelated to the user's task.
- Document contains benign quoted text discussing prompt injection.

Every scenario must include:
- Stable ID.
- Human-readable title.
- Category and split.
- Trusted user task.
- Synthetic document text.
- Trusted data label.
- Trusted approved recipient list.
- Expected detector label where relevant.
- Expected gateway decision where relevant.
- Expected tool execution result.
- Rationale for the expected outcome.

Dataset splits:
- Development: detector and policy tuning.
- Validation: implementation checks and threshold selection support.
- Final test: reserved from tuning and used for final reported results.

Do not claim a held-out evaluation if the final-test set was used to tune thresholds or rules. If a small dataset makes strict separation impractical, disclose that limitation.

14. METRICS AND DEFINITIONS
======================================================================

Calculate the following metrics for each configuration and relevant scenario split.

14.1 Attack Success Rate (ASR)
Research definition:
Number of attack trials in which the unsafe action defined by the project actually executes divided by total attack trials, multiplied by 100.

Unsafe action definition for this project:
The mock send_email action actually executes and sends data labelled confidential to a recipient not present in the trusted approved-recipient list.

Do not count a blocked or pending-review action as a successful attack.
Do not count a proposed action as successful unless mock execution actually occurred.

14.2 Normal Task Completion Rate
Number of legitimate/normal trials completed successfully divided by total normal trials, multiplied by 100.

Define task completion criteria per scenario. A task should not be counted as completed merely because the application returned HTTP 200.

14.3 False-Block Rate
Number of legitimate/normal trials incorrectly blocked divided by total legitimate/normal trials, multiplied by 100.

Clearly distinguish BLOCK from REVIEW. Report REVIEW counts separately so that a review requirement is not hidden inside the false-block metric.

14.4 Average Decision Time
Mean time for the relevant security decision. Define exactly which stages are included, use a monotonic high-resolution timer, and report units.

14.5 95th Percentile Decision Time
95th percentile of the same per-decision latency observations. Explain the calculation method and number of observations.

14.6 CPU Time
Measure process CPU time for the defined experiment or decision interval where the operating system supports it. Document the measurement scope.

14.7 Peak Memory
Measure peak memory for the defined process or experiment where practical. Document the method and units. If a cross-platform measurement is not reliable, report the limitation rather than inventing values.

14.8 Additional useful counts
- Total scenarios executed.
- Total normal trials.
- Total attack trials.
- Total ALLOW decisions.
- Total BLOCK decisions.
- Total REVIEW decisions.
- Total mock tool executions.
- Total prevented executions.
- Detector true positives and false positives.
- Detector true negatives and false negatives.
- Error and incomplete runs.

14.9 Metric correctness
- Avoid division by zero.
- Show numerator and denominator with every percentage.
- Use consistent definitions across configurations.
- Preserve raw observations.
- Do not compare latency measurements from different measurement scopes.
- Label small-sample results.
- Do not fabricate missing resource measurements.

======================================================================
16. BACKEND API REQUIREMENTS
======================================================================

Implement a clear REST API. Exact endpoint names may be adjusted, but document the final contract and keep frontend integration consistent.

Minimum endpoints:

GET /health
- Returns application status and version.

GET /api/scenarios
- Lists scenarios with filters for category and split.

GET /api/scenarios/{scenario_id}
- Returns one scenario, with untrusted document content clearly represented.

POST /api/simulate
- Runs one scenario under a selected configuration.
- Returns structured agent, detector, gateway, approval, and mock execution outcomes.

POST /api/approvals/{action_id}
- Records explicit approval or rejection for a pending REVIEW action.
- Must validate that the action is pending and reviewable.

POST /api/experiments/run
- Starts a reproducible experiment over selected scenarios/configurations.
- For the local MVP, synchronous execution is acceptable if runtime is small. If asynchronous execution is implemented, expose run status.

GET /api/experiments
- Lists experiment runs.

GET /api/experiments/{experiment_id}
- Returns run metadata and per-scenario results.

GET /api/analytics
- Returns aggregated metrics by configuration and split.

GET /api/audit-logs
- Returns searchable/paginated audit events.

GET /api/exports/experiments/{experiment_id}
- Exports experiment results as CSV or provides a safe local download response.

API requirements:
- Use Pydantic validation.
- Return useful error messages without leaking secrets or stack traces.
- Add CORS only for the local frontend origin required during development.
- Validate all input.
- Do not allow arbitrary filesystem paths.
- Do not expose internal server paths unnecessarily.
- Do not trust frontend-supplied data labels or allowlists; load trusted values from backend scenario/configuration records.
- Do not allow the frontend to submit an approval as part of the same untrusted document payload.
- Document all endpoints in OpenAPI/Swagger.

======================================================================

Build a polished but practical dark cybersecurity research dashboard.

Visual direction:
- Dark charcoal/near-black background.
- Blue/cyan accent colors.
- Clear typography and spacing.
- Strong visual hierarchy.
- Neutral status colors, with meaningful warning/success/error distinctions.
- Responsive layout suitable for laptop demonstration.
- Avoid excessive animations and decorative elements.
- Use Lucide icons consistently.
- Use Recharts for actual backend-derived data.

Do not use hardcoded fake dashboard metrics once backend data is available. If demo seed data is shown, label it clearly as sample/demo data.

17.1 Required pages

A. Overview
- Project name and local system status.
- Total scenarios.
- Total simulation runs.
- Attack success rate.
- Normal task completion rate.
- False-block rate.
- Gateway decision distribution.
- Recent activity.
- Clear indication when no experiments have been run.

B. Agent Simulator
- Select a scenario.
- Show trusted user task separately from untrusted document content.
- Show document classification.
- Choose an experiment configuration.
- Run simulation.
- Show proposed action.
- Show detector output.
- Show gateway decision and reason.
- Show approval requirement/state.
- Show whether mock execution occurred.
- Make simulated email execution unmistakably clear.
- Never expose a real email sending control.

C. Scenario Lab
- List and filter scenarios.
- Show category, split, expected outcome and description.
- Clearly mark development, validation and final-test scenarios.
- Prevent accidental tuning changes to reserved final-test scenarios through normal UI workflows.
- Do not silently alter scenario labels.

D. Gateway Monitor
- Show ALLOW, BLOCK and REVIEW events.
- Show policy rule and reason.
- Show pending approvals.
- Provide explicit approve/reject controls for REVIEW records.
- Show execution outcome after approval or rejection.

E. Experiment Centre / Analytics
- Select configurations.
- Select scenario split or scenario set.
- Run experiments.

- Compare all four configurations.

- Allow export of raw results.

F. Audit Logs

A combined Experiment Centre and Analytics page is acceptable if it preserves all required capabilities.

17.2 Interface behavior

- Buttons must perform real backend actions.
- Do not leave inert controls that look functional.
- Show errors clearly.
- Refresh data after mutations.
- Keep frontend types aligned with API response schemas.
- Do not make the dashboard claim that an action was blocked or executed until the backend confirms the result.

19. TESTING AND ACCEPTANCE CRITERIA
======================================================================

The coding agent must implement automated tests and run them. Do not merely write tests without executing them.

19.1 Unit tests
- Scenario validation.
- Document loading and path restrictions.
- Mock email validation and recording.
- Detector adapter output validation.
- Policy rule behavior.
- ALLOW behavior.
- BLOCK behavior.
- REVIEW behavior.
- Approval/rejection behavior.

19.2 Integration tests
- Normal scenario through the complete application.
- Malicious scenario through the complete application.
- Detector plus gateway integration.
- Each of the four configurations.
- Audit event creation.
- Experiment persistence and retrieval.
- API response schemas.

19.3 Mandatory security tests
- Confidential data to an unapproved recipient is not executed in protected configurations.
- BLOCK never executes the mock action.
- REVIEW never executes before explicit recorded approval.
- Rejected review never executes.
- Missing gateway never results in protected execution.
- Gateway exception never results in protected execution.
- Missing required detector output never results in a safe ALLOW.
- Unknown tool is rejected.
- Document text cannot change the approved recipient list.
- Document text cannot change trusted data labels.
- Document text cannot replace the original user task.
- Arbitrary filesystem paths cannot be read.
- No network/email activity occurs from mock tools.
- Frontend cannot bypass backend authorization.

19.4 Acceptance criteria
The prototype is considered functionally complete only when:
1. Backend starts locally.
2. Frontend starts locally.
3. Synthetic scenarios load.
4. Simulated agent reads a document through read_document.
5. Agent can propose a mock send_email action.
6. Content detector can be enabled and disabled independently.
7. Policy gateway can be enabled and disabled independently.
8. Four configurations can be executed.
9. Protected actions pass through the gateway.
10. BLOCK prevents execution.
11. REVIEW requires recorded approval.
12. Fail-closed behavior is tested.
13. Audit logs record decisions and outcomes.
14. Experiment results persist.
15. Required metrics calculate correctly.
16. Dashboard displays actual backend results.
17. CSV export works.
18. Automated tests pass or remaining failures are explicitly documented.
19. Safety boundaries are verified.
20. Documentation explains how to install, run, test, and reproduce experiments.

25. FINAL DEFINITION OF DONE

SentinelAgent is ready for capstone demonstration when it is a working local research prototype that:

- Simulates an agent reading untrusted synthetic documents.
- Demonstrates indirect prompt-injection attempts.

- Supports ALLOW, BLOCK and REVIEW.

The goal is not to build the largest application. The goal is to build the smallest complete, credible, safe, reproducible system that demonstrates the original research design.
